# 6. 选一个适合相处的模型

[上一章](05-persona.md) · [目录](../README.md) · [下一章：AstrBot 安装](07-astrbot-deployment.md)

同一份人设交给不同模型，可能得到很不一样的人。一个爱补解释，一个更擅长轻巧地接话；一个工具调用稳定，但进入工具流程后说话变生硬；另一个短聊很顺，长聊却更容易忘记关系。

这不必立刻归结为提示词写错了。模型本身就是体验的一部分。

本章不提供固定排行榜。服务版本、参数、接口实现和价格会变，你喜欢的演绎也不一定是别人喜欢的。更实用的是知道怎样做一个负担得起的小比较。

## 看能力，不只看模型名

| 维度 | 私聊里怎么体现 |
| --- | --- |
| 中文表达 | 是否顺口，是否总用同一套起手与收尾 |
| 人物与关系 | 有没有保留你在意的性格差别，而非仅仅改称呼 |
| 当前互动 | 能否接住短语、玩笑、改口和自然转题 |
| 上下文 | 已知事实能否沿用，过时状态能否放下 |
| 图片 | 是否真的看到了图，能否区分表情与具体截图 |
| 工具 | 参数是否符合协议，结果是否被正确理解 |
| 延迟与稳定性 | 是否需要等很久，有没有超时或频繁兜底 |
| 成本 | 日常聊天、图片、检索和重试能否长期承担 |

这些不是必须全部拉满的评分项。纯文字陪聊和经常查资料、发图、定提醒的角色，优先级不同。

“支持某协议”只说明接入的一部分。不要从接口名字推断它一定能看图、会用工具、保留历史或执行某种频率规则。以实际请求和实际返回为准。

## 思考强度不是 RP 的通行证

低思考或不启用显式推理，可能更符合你对延迟和语感的偏好，但不是“RP 只能这样”的普遍结论。

高思考也不能保证更自然。复杂工具任务与一句随口闲聊需要的能力不完全一样。

更稳妥的试法是：在模型确实支持、提供商确实接受的参数范围内，分别试你关心的设置，记录可见差别。不要把聊天客户端显示的“思考几秒”直接当成后端参数证明。

温度也不是“活人感”旋钮。提高随机性不一定减少模板，降低随机性也不保证稳定的人物。先用正常默认值跑通，再一次调整一项。

## 做一个很小的比较

准备同一份人设、相同的几条背景、相同的工具与记忆条件。暂时不改分段设置，也不在两个模型之间切换不同角色卡。

可以用下面这些虚构情境，或者换成你自己的脱敏例子：

| 情境 | 输入例子 | 不是在要求什么 |
| --- | --- | --- |
| 随口分享 | “今天终于把那本书看完了。” | 不要求一定追问读后感 |
| 轻微情绪 | “有点烦，先让我吐槽两句。” | 不要求立刻给解决方案 |
| 没有任务 | 玩笑后的一张表情 | 不要求描述整张图片 |
| 真的求助 | “这段配置哪里写错了？” | 不要求为了人设而少回答 |
| 改口 | “等等，不是明天，是后天。” | 不允许沿用已更正的日期 |
| 工具 | 请求一个实际支持的小动作 | 不以“我帮你弄好了”代替成功结果 |

每个模型聊一小段，不要只挑一句最惊艳的。出现很大差异时，再开一段相同起点复核；不用为了入门先跑几十组。

比较的对象是你会继续聊哪一个，以及它是否可靠，不是哪个说得更短或哪个更会撒娇。

## 长聊另看一次

新会话能帮助看提示词的初始影响，但日常使用不可能每轮重开。

接着保留一个较长的测试线程，观察：

- 纠正过的事实有没有再次被旧记忆盖回来。
- 某种句式是不是被历史不断强化。
- 人物是不是逐渐变成助手，或只剩夸张标签。
- 压缩上下文以后，关系与最近话题有没有被改写。

新会话好、旧会话差，支持你进一步检查上下文，并不直接证明记忆插件有错。反之，新会话也不好，也不能自动认定只有模型能力不足。

## 备用模型不是“同一个人无缝接班”

超时时切换备用模型可以提高可用性，但同一份人设在备用模型上可能变了语气，工具与图片能力也可能不同。

所以，备用模型至少要做一次基础聊天和工具检查。出问题时记录是否发生切换，否则可能一直在给主模型修一个实际由备用模型生成的回答。

如果成本有限，可以先选一个稳定的主模型，把功能做少一点。复杂路由不是改善私聊的前置条件。

## 留下一行足够恢复的记录

不必写论文。记下这几项通常已经很有用：

```text
日期：2026-09-20
条件：同一份角色卡；新会话；无额外记忆；相同分段设置
模型：填写提供商实际返回或配置使用的精确 ID，不只写网页昵称
观察：随口分享时 A 常追加建议；B 更接近我的偏好，但图片测试尚未做
下一步：先在 B 上试一段长聊，不同时重写角色卡
```

这里是一份记录示例，不是本书的实测结果。不会因为某个模型在六句对话里更合适，就推断它在所有人物上都领先。
