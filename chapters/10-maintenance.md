# 10. 插件怎么加，系统怎么养

[上一章](09-debugging.md) · [目录](../README.md) · [文章副本](../articles/README.md)

当系统终于比较好聊，最容易做的事是继续添加功能。记忆、主动消息、搜索、语音、表情、状态模拟，似乎每一种都能让角色更完整。

但完整不等于全装上。一个插件改变模型输入，另一个负责发送，第三个又自己请求模型；它们单独能用，合在一起可能出现重复回复、上下文错位和取消不干净。

## 每次增加一个明确能力

先写一句你遇到的问题：

> 用户经常分三条把话说完，机器人却逐条回复。

再找解决这个问题的能力：

> 把短时间内的连续输入合并后处理。

最后才选择插件。这比“装一个拟人化插件试试”更容易验收，也更容易决定不装哪些功能。

对于 TurnFlow，重点看连发、打断、撤回和完成后的正常新轮次。对于表情包管理器，重点看选包、纯图、标签清理与失败处理。不要仅仅检查管理页是否出现。

## 同类能力先只留一个

装新插件前，在 AstrBot 插件页核对已启用的插件，也留意宝塔编排中是否另有负责收发的服务：谁接收消息，谁压缩或检索记忆，谁改提示词，谁负责发送。**同一环节先只留一个负责者**，尤其别同时打开两个自动记忆、两套防抖中断，或两套接管发送的插件。

例如装了两份记忆插件，它们可能各自从向量库找回旧聊天，并在同一次请求里注入两份内容。角色忽然翻旧账或反复确认，并不一定是模型自己“想太多”，先看实际注入是否重复。停用一个插件也要核对剩下的数据库和旧上下文，不要以为插件开关会自动清除历史记录。

确需叠加时，先搞清两者处理的是不是不同事件、先后顺序怎样、能否取消和回退，再用一段相同的测试对话验证。不是说同类型插件在技术上绝对不能共存，而是日常私聊没必要先把冲突留给用户体验来发现。

## 多个插件一起用时，检查交界处

| 组合 | 需要观察 |
| --- | --- |
| 防抖 + 图片转述 | 多张图与文字次序是否保留，转述是否重复 |
| 回复中断 + 表情发送 | 旧文本停止后，晚到的图是否仍被发出 |
| 输入状态 + 回复中断 | 旧轮次停止后是否还显示“正在输入”，新轮次是否正常开始 |
| 分段 + 表情标签 | 标签有没有被拆坏或裸露 |
| 主动任务 + 自定义发送插件 | 是否经过相同的人设与消息处理，是否发到正确会话 |
| 主动聊天插件 + FutureTask | 两种触发是否向同一会话重复发信，暂停后是否都停下 |
| 检索记忆 + 压缩摘要 | 是否把同一段旧事实重复注入或复活过期状态 |
| 手动遗忘 + 检索记忆 | 会话历史删掉后，外部索引是否仍回注那段内容 |
| 备用模型 + 工具 | 切换后工具协议与图片能力是否仍可用 |

并不是每一项都要在第一天做。你确实使用了哪一种组合，就优先验证对应位置。

特别是“插件自己调用模型再发消息”的路径，可能绕过正常管线。表情包管理器提供了[公开联动接口](https://github.com/anka-afk/astrbot_plugin_meme_manager/blob/92de79e441bb55d7159067edcc48adbb2d2f4015/DEVELOPMENT.md)，但第三方插件是否调用，还需要检查；接口存在不等于自动接好了。

## 需要开发时，先做小需求

[《我做 AstrBot 插件这一年,最值钱的其实不是代码》](../articles/astrbot-plugin-dev-experience.md)里有一个值得沿用的取舍：先解决真实遇到的小问题，再根据反馈扩展。

可以把给开发者或编程模型的需求写成这样：

> 这个插件只处理私聊输入合并。保留图片与文字的相对次序，不影响指令消息，不修改群聊。先给出它在当前 AstrBot 版本中接入的位置、一次收集的结束条件和失败时的退路，再实现最小版本。

这比“让机器人像真人一样思考”更可实现，也更能知道做完了没有。

但不要把旧文章附带的所有开发建议都当成当前 API 规范。嵌套配置、页面路径、事件钩子和发送接口，应对照[当前插件文档](https://docs.astrbot.app/dev/star/plugin-new.html)与目标版本源码。经验笔记用于提醒哪里容易出事，不代替接口定义。

## 升级前知道怎么回去

至少保留：

- 当前程序、协议端、插件和镜像版本。
- 当前角色卡与相关模板。
- 配置和必要数据的一致备份。
- 这次升级改了什么，以及一套最短的收发测试。

先阅读迁移说明。代码回退不保证数据库或插件数据也能倒退；不要直接把旧镜像压回升级后的数据目录，期待一定能恢复。

备份最好不在同一份公开仓库中。真实聊天、登录状态、token、API Key 和自动收集的私人图片都不适合作为教程样本。

## 出错时，少留一点但留对信息

给项目维护者反馈时，通常需要版本、平台、发送模式、最小步骤和脱敏错误日志。

“不自然”可以附一小段获准分享的对照，说明想保留与想改变的部分；“发不出去”则需要发送返回或相关日志。两类问题不要都用一张没有上下文的聊天截图代替。

不要公开完整请求中的凭据，也不要把私人会话批量交给不明日志收集服务。

## 一份可以停下来的检查清单

下面都符合你的使用范围时，就可以先正常聊一段时间，而不是立即继续加功能：

- 基础消息能够稳定收发。
- 连续补充不会明显制造过时回复队列。
- 图片和表情按实际内容处理，也可以只发表情。
- 人物保留了你希望留下的特点。
- 真正的求助仍能获得足够回答。
- 工具做没做成，系统分得清楚。
- 主动联系的范围、暂停与取消由你掌握。
- 有备份，知道下一次改坏了怎么恢复。

这不是要求每个机器人都具备所有能力。没有使用工具或主动消息，就不需要为它们安装一整套系统。

最后，聊天终究不是一串功能勾选。工程让消息能够正确来回，模型决定具体如何回应，人设让这个回应属于你想写的人。把这三件事放在合适的位置，往往比不断要求模型“更像真人”更值得做。
