# 8. 记忆、时间与主动联系

[上一章](07-astrbot-deployment.md) · [目录](../README.md) · [下一章：排查方法](09-debugging.md)

搭好基础聊天以后，最容易让人想继续加的，通常是记忆和主动消息。不过，长聊首先遇到的是上下文怎样留下来，而不是该装哪一个记忆插件。

这些能力可能增加连续感，但不是打开就自动“更像人”。一句从旧摘要里抄来的关心，可能比不记得更突兀；一份创建成功却没有触发的提醒，也不能靠台词挽回。

这一章把“角色知道什么”和“系统能做什么”放在一起讨论。

## 先分清四种材料

| 材料 | 适合放什么 | 常见问题 |
| --- | --- | --- |
| 人设 | 稳定的性格、关系设定、表达方向 | 把每件日常小事都永久写进去 |
| 近期对话 | 正在聊什么、语气如何变化、刚纠正了什么 | 被过早截断，或塞入太多无关工具日志 |
| 压缩摘要 | 旧对话里仍有用的事实、纠正、关系脉络 | 推测变事实，最近的语气被概括掉 |
| 检索式记忆 | 经过选择、需要跨会话找回的资料 | 旧状态被检索回来，多个来源重复注入 |

例如，“用户这周要出差”不是永久身份。“用户不喜欢被叫某个昵称”也不是一句转题后就该忘掉的临时状态。

压缩摘要仍属于当前对话的上下文维护；检索式记忆则多了入库、检索与回注的环节。它们不是一回事，也不必同时启用。

## 先看每次请求到底带了什么

普通私聊通常不需要每句话都调用搜索、浏览器或一串生产工具。用户与角色的几句对话可能很短，真正把请求撑大的反而是工具定义和返回、长人设、平台说明、插件提示及重复的记忆注入；具体占多少，要看宿主实际发出的请求，不能凭聊天气泡数量猜。

本书对聊天型 bot 的默认建议是：先保留聊天必需的能力，有确切需求再加工具。需要提醒就接入可核验的调度，需要表情就接入发送能力；不要为了“更像 Agent”把一套检索、生产和自动化工具全挂到每次闲聊上。关掉没有用的工具后，也检查它的说明和插件注入是否真的从请求中消失。

纯聊天也不必因为模型支持百万 token，就把窗口开到最大或一直填满。对支持相应长度的模型，**10 万到 30 万 token**可以作为长聊的一个观察范围，而不是最低要求、统一最佳值或实际每轮都要消耗的量。许多对话用得更少；上下文太长时，成本、延迟和对早期细节的利用都值得实测。先确认提供商支持的窗口、实际输入 token、预留的输出空间，再看超长会话是否真的比压缩后的会话好聊。

## 不要把摘要当监控记录

用户说“最近有点累”，不等于确认了原因，更不等于以后每晚都应该被问一次有没有好转。

旧摘要里写“用户在旅行”，也不能直接推出此刻仍在旅行。没有可靠时间时，不要让系统假装已经知道过去了几小时或几天。

角色可以根据关系表达想念、无聊、期待，这些不必每次都找一个外部事实来许可；但“你答应过”“你又熬夜”“你刚才在外面”需要实际依据。

这一点对第一人称与写作视角都成立：**看到了后台材料，不等于可以把所有材料当成角色亲眼见到的现实。**

## 优先试压缩，再决定是否要检索记忆

相比到达阈值后按轮数直接扔掉旧对话，本书更倾向于先试 **模型压缩摘要 + 保留近期原文**：让旧话题、已纠正的事实和仍有效的关系脉络留下来，同时把大段工具输出与过期过程清掉。摘要不是自动清洗器，写坏了照样会编事实、丢语气；要留原始对话的可恢复副本，观察压缩前后实际变化。

AstrBot 的[上下文压缩文档](https://docs.astrbot.app/use/context-compress.html)说明，默认策略是按轮数截断；选择 LLM 压缩时可指定摘要模型、保留近期轮次并调整摘要提示词。先在 WebUI 的“配置文件 → AI 配置 → 高级 → 上下文管理策略”里检查当前选项，再到“模型提供商 → 对话”核对模型的 `max_context_tokens`。如果窗口无法识别且仍为 0，自动压缩可能不会触发；没有选摘要模型时也可能退回截断。若另有“最多携带对话轮数”，也要确认旧对话是否早在摘要触发前就被裁掉。按你的版本界面和日志确认，别以为点了“压缩”就已经生效。

AstrBot 文档中的默认摘要模板会提到项目进度和工具调用。这对办事有用，对闲聊则未必是最想保留的内容。可以让摘要优先留下仍相关的话题、明确偏好、已确认的改变与尚未完成的约定，把旧工具日志压成必要结果；不要把推测、玩笑和未执行的动作写成既定事实。是否改模板，仍要看一份真实摘要，而不是仅凭名称判断。

可以先检查一份真实摘要：

- 用户的猜测有没有被写成确认事实。
- 开玩笑的话有没有被当作长期约定。
- 最近已经澄清的事情是否仍旧记错。
- 未完成工具是否被写成已完成。
- 是否保留了当前仍相关的互动，而只剩零散资料。

先修最明显的一项，再比较压缩后的聊天。不要同时换摘要模型、主模型、人设和记忆插件。

压缩本身还会调用模型，产生额外费用与一次出错机会。AstrBot 当前文档也说明，工具调用过程内部暂不压缩，压缩后仍超限时会继续裁剪；所以少挂高噪声工具和设置压缩策略是两件互补的事。

## 检索式记忆，默认可以先不用

本书不建议为了日常私聊一开始就安装自动记忆插件。常见实现会将选定的对话或提取结果入库、生成向量，查询时检索回相关片段；有的还会使用重排序，但不是每个插件都这样，也不是每条坏回复都会自动入库。关键要看它**实际收录什么、什么时候回注、能不能更正和删除**。

如果插件自动收录了误解、过期状态或一次不满意的角色回复，后续检索可能反复把它带回来。长期使用还得同时维护原始会话、摘要和额外索引或数据库，并处理备份、删除及隐私范围。先用“近期原文 + 必要时的压缩摘要”聊一段；只有确实需要跨会话找回大量资料、愿意维护入库规则和纠错流程时，再单独试检索式记忆。

若要试，先限定一个会话、一个插件，抽查入库内容和回注片段，并实际试一次纠正与删除。不要把“检索命中”当成那段资料必然真实，也不要再同时启用另一份会注入相似资料的记忆插件。

## 只想删掉最近一次不满意的回复

不必为了一轮答歪的聊天就重写人设，或者直接丢掉整条会话。[llm_amnesia](https://github.com/SinkAbyss/astrbot_plugin_llm_amnesia) 提供手动指令：`/forget` 从当前 AstrBot 会话历史删除最新一轮，`/forget 3` 则删最近三轮（该版本支持一次 1 到 10 轮）。想反悔可在接着聊天前用 `/cancel_forget` 恢复；要重新回答，仍需自己再发送那句消息。该版本 README 要求 AstrBot v4.28.0+、Python 3.12+，安装前先核对环境。动手前备份重要对话，确认删的是当前会话，不把插件命令当作“让模型忘掉一切”的永久开关。

例如用户说“有点睡不着”，机器人却连发几段不喜欢的关怀话术。若只是这次回复会把后文带偏，可以先手动移除这一轮，再按自己的意思继续；若同样的问题每次重现，就应回到第 9 章检查当前人设、模型和注入，删历史本身不会修好生成方式。

这个插件改的是 **AstrBot 会话管理器里的对话历史**。QQ 窗口已显示的消息、先前压缩出的摘要，以及其他记忆插件自己的向量库，不会因为这里删了一轮就当然一起消失。项目 README 提到“RAG 兼容”，指的是处理被注入内容的回显，不能理解成它替你清空了外部记忆库。如果同时使用检索式记忆，下次请求仍可能重新注入被删内容；需要分别核对它们的入库、纠错和删除方式。

## 换人设时，给旧对话一个干净的入口

情境：你改掉了角色卡里惯性追问的写法，却想保留过去聊过的事。如果直接在旧线程替换人设，旧回复仍是模型眼前的示范。它可能继续学那些连问或固定起手式；这不是每次都会发生，但值得和干净新会话对照。

做法是**备份旧会话，在副本上整理，再用新的人设开新会话**。只删最新一轮适合局部失误；换人设涉及一整段旧回复时，手动删一两轮未必足够。不要直接删除原线程，也不要把旧记录里“不好的回复”逐条贴进新会话并解释为什么不好。保留的是经过确认的事实、用户明确偏好、当前话题与还没完成的约定，不是旧角色每一句的语气。旧摘要、记忆插件和额外注入也要一起检查，否则新线程仍可能被旧材料带偏。

整理时可以把脱敏后的旧对话和新版人设中**允许分享的目标与偏好**交给另一个模型，请它只做交接摘要。仓库提供一份可直接用于网页聊天端的[摘要请求文本](../examples/conversation-handoff-prompt.txt)：它覆盖长期主线、已讨论结论、最新焦点、关键配置、明确偏好、失败尝试和下一步；没有的项目写“无”，不要为了填满栏目而补故事。发往外部服务前，先删去账号、密钥、真实身份、私人图片、隐藏提示词和无关工具日志，并确认你接受对方处理这些内容。摘要回来后还要自己核对：用户改口是否保留、猜测有没有变成事实、旧回复的口癖有没有混进“用户偏好”。

该请求要求返回**单行 JSON 字符串字面量**，便于放进历史记录的 `text` 字段：整个结果由双引号包住，内部换行写成 `\n`，引号写成 `\"`；换行转义是反斜杠 `\n`，不是 `/n`。它不是让模型生成 Markdown 报告，也不是把整个旧线程或新版人设原文压成一条大消息。手动粘贴到普通聊天框时，先把这层 JSON 字符串解析为正文，别连外层引号和反斜杠一起贴进去。

新线程应先启用**新的人设**。有些宿主需要先发一句“你好”才能建立会话，再由管理者导入历史；有些可以直接放入一条明确标为“历史对话摘要”的用户侧上下文。下面的[消息数组示例](../examples/conversation-handoff-history.example.json)只说明有编辑历史能力时的一种放法：一条合成的 `user` 摘要消息，必要时紧跟一条合成的 `assistant` 确认。`已收到` 只是历史占位，不是要求角色每次这么说，更不能冒充真实用户新说的话。如果宿主允许单条摘要消息，就不需要伪造确认回合。

这份数组**不是 AstrBot 会话数据库的通用导入文件**。AstrBot 当前提供 `/new` 建立空对话，管理页可以导出旧对话，但原始历史 JSON 预览是只读的；能否插入 `content` 数组、是否要求交替角色、怎样保证新会话 ID 和平台注入正确，都必须按你使用的宿主与版本核验。没有可靠导入方式，就通过正常聊天入口发送经过核对的摘要，不直接改运行中的数据库。示例中也不放旧时间的 `<system_reminder>`：当前时间若有意义，应由新会话的宿主按当前时钟提供，而不是把旧导出的日期当今天。

之后用一两段普通聊天检查：角色能否接住确实发生的近况，旧口癖是否仍大量出现，新人设有没有被摘要压扁。换线程是减少旧示范影响的办法，不是保证新稿有效的证明；若新会话仍有相同问题，再回头看新人设、模型和当前注入。

## 时间信息是能力，不是常识

模型知道日期是什么，不代表这次调用知道当前日期。宿主提供了时间，也要留意时区、格式和任务触发时间是否一致。

不过，没有绝对日期不代表所有未来任务都不能做。宿主若支持“十分钟后”这样的相对延迟，就应依据实际协议处理，不必人为设置一个“必须先确认年月日”的障碍。

人设里也不应该虚构一个永远准确的内置时钟。需要哪种时间依据，看当前动作，而不是每轮都把时间确认一遍。

## 主动联系，不必每次都是任务提醒

朋友会因为想到你来找你，也会分享一件小事。亲密角色可以直接说想被陪着，不必都伪装成吃饭、睡觉或工作检查。

宿主可以提供主动触发机会，但触发本身不证明用户想被打扰，也不证明用户故意冷落了角色。频率、静默时段、暂停和未回复后的行为，应由可控的宿主设置承担一部分。

一种较清楚的偏好说明是：

> 我接受这个角色主动来找我，也接受普通的生活提醒。北京时间 23:00 到次日 08:00 不要主动发消息，暂时不回复时不要连续催。暂停以后不再主动联系，等我重新开启。

这是供使用者设定自己的范围，不是本书统一规定的时段或频率。角色的主动程度也可以不同。

### 插件触发的主动聊天

私聊里角色偶尔自己来找你，一般不是模型在后台“想起来了”，而是宿主或插件等到触发条件，再请求模型生成一条消息。例如 [astrbot_plugin_proactive_chat](https://github.com/DBJD-CR/astrbot_plugin_proactive_chat) 可以按会话沉默后的时间间隔触发主动消息；它提供私聊会话列表、免打扰时段、未回复次数上限与主动消息提示词。启用前先核对目标会话标识、时区和这些设置，不要只在人设中写“你可以主动找我”就期待消息自己发出来。

这类插件可能用模拟的用户消息启动一次模型请求。**触发提示不是用户真的刚发了新消息**，也不是一项已安排好的提醒。插件自己的 `proactive_prompt` 需要让模型看懂这个区别，同时沿用当前会话的人物，不另造一位“负责主动联系”的角色。下面是可以放在该插件私聊主动消息提示词里的简例；两个双花括号字段是此插件提供的占位符，换插件要按它的实际字段改：

```text
【主动联系】
这是宿主触发的一次私聊主动发言机会，不是用户刚发来的话。沿用当前会话的人设与关系，写角色这次自己想说的话。
当前时间：{{current_time}}
连续未回复次数：{{unanswered_count}}
角色可以因为想念、无聊、想分享或想被陪而开口，不必先问用户在忙什么。旧话题可以顺带提，但不把过去的状态当成现在的事实；未回复次数不证明用户故意不理你。只输出发给用户的消息，不附任务说明。
```

这段只标明**触发情境与事实边界**，不替不同角色规定语气、长度或气泡数。若角色本来会撒娇，也不需要把“未回复两次就委屈”写成固定公式。插件自己的定时、静默、暂停和发送链路才决定消息能否发出；装了表情包插件，也要单独试主动消息是否真的能只发图、是否与普通回复经过同一条处理路径。

先只给一个获准的私聊会话启用，核对主动消息的实际显示、停发和收到用户新消息后的行为。若另一插件也会主动发信，检查它们是否会在相近时间重复联系同一个人。

## FutureTask：把以后要做的事交给真实调度

核对的 [AstrBot 主动型能力文档](https://docs.astrbot.app/use/proactive-agent.html)将 FutureTask 列为实验性功能，并提供在后台查看、编辑和删除未来任务的入口。界面位置与支持范围应以你的版本为准。

它处理的是**已经安排在未来执行的具体任务**，例如稍后提醒或联系；上面的插件则按会话沉默等条件提供普通的主动聊天机会。二者都可能发出主动消息，但触发依据、记录位置和取消办法不同，不应靠同一段提示词假装它们是同一个功能。

这里至少有几个不同状态：

```text
角色表达打算
  → 模型发起有效调用
  → 宿主接受并创建任务
  → 到时触发
  → 任务执行
  → 消息投递
```

前一个状态不自动保证后一个。尤其是“任务已创建”不等于“明天一定送达”。

工具也不一定只有一个固定名字。提示词应服从宿主实际注册的定义，不用凭一篇文章猜工具名称、参数和成功条件。

### 保留主动性，不把授权写成层层关卡

用户可以直接请求提醒，也可以事先授权一类日常提醒或稍后联系。已经有适用的持续授权时，不需要每次重新征求同样的许可。

时间不精确时，也不必总是反问。若授权范围允许、场景足以作出低风险的合理选择，可以按可用工具安排并让用户知道；真正无法判断或后果明显不同，再澄清。

相反，面向新收件人、修改重要资料、付费等动作，不应从“允许主动私聊”里顺手推出授权。这是在区分动作范围，不是在把普通联系变成审批流程。

### 失败也要保留事实

请求超时不一定等于根本没执行。对可能创建重复任务的操作，先查状态或利用实际支持的去重机制，不要盲目重复。

工具成功后，角色可以自然表达结果，不需要念一串内部函数名。但用户问“真的设上了吗”，就应该能基于结果回答，而不是为了沉浸感回避确认。

## 做一次小验收就有帮助

从一个低风险、短延迟、可删除的测试任务开始：

1. 确认它出现在任务列表，而不只是聊天里说了“好”。
2. 到点查看是否触发、是否送到正确会话。
3. 试着删除另一个测试任务，确认不会继续发送。
4. 如果你依赖重启后仍有效，再单独验证任务是否持久化。

主动聊天与普通回复还要共享同一套人物设定。插件触发入口和任务入口都不应突然变成另一种口吻，也不应绕开你已经设置的暂停。

最后，提醒可提升体验，但不应被当作唯一可靠的现实保障。重要事项需要使用你能够确认可靠性的提醒渠道。
