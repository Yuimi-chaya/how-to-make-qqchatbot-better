# 8. 记忆、时间与主动联系

[上一章](07-astrbot-deployment.md) · [目录](../README.md) · [下一章：排查方法](09-debugging.md)

搭好基础聊天以后，QQ 机器人和普通聊天模型的差别，才会慢慢显出来：它能不能接住昨天聊到一半的事，能不能知道现在是深夜，能不能在你没有发消息时主动来找你，能不能记得“明早叫我”不是一句客套话。

这些体验不来自同一个“记忆”开关。记忆让角色接得上过去，宿主提供的当前时间让它处在此刻，主动消息让它有机会先开口，FutureTask 则让它和约定好的未来发生联系。本章按这条时间线讲，而不是按插件列表讲。

## 先让过去服务于现在

| 材料 | 适合放什么 | 常见问题 |
| --- | --- | --- |
| 人设 | 稳定的性格、关系设定、表达方向 | 把每件日常小事都永久写进去 |
| 近期对话 | 正在聊什么、语气如何变化、刚纠正了什么 | 被过早截断，或塞入太多无关工具日志 |
| 压缩摘要 | 旧对话里仍有用的事实、纠正、关系脉络 | 推测变事实，最近的语气被概括掉 |
| 检索式记忆 | 经过选择、需要跨会话找回的资料 | 旧状态被检索回来，多个来源重复注入 |

例如，“用户这周要出差”不是永久身份。“用户不喜欢被叫某个昵称”也不是一句转题后就该忘掉的临时状态。

压缩摘要仍属于当前对话的上下文维护；检索式记忆则多了入库、检索与回注的环节。它们不是一回事，也不必同时启用。

## 不要把所有东西都塞进现在

普通私聊通常不需要每句话都调用搜索、浏览器或一串生产工具。用户与角色的几句对话可能很短，真正把请求撑大的反而是工具定义和返回、长人设、平台说明、插件提示及重复的记忆注入；具体占多少，要看宿主实际发出的请求，不能凭聊天气泡数量猜。

这也是为什么“模型支持更长上下文”不等于“把所有东西都塞进去会更像真人”。人类聊天会忽略大量无关背景，模型却会把收到的材料当作当前任务的一部分来处理；噪声越多，真正重要的关系线索越容易被稀释，工具结果也可能抢走本来只需要一句回应的场景。

本书对聊天型 bot 的默认建议是：先保留聊天必需的能力，有确切需求再加工具。需要提醒就接入可核验的调度，需要表情就接入发送能力；不要为了“更像 Agent”把一套检索、生产和自动化工具全挂到每次闲聊上。关掉没有用的工具后，也检查它的说明和插件注入是否真的从请求中消失。

纯聊天不用追求百万 token 窗口。上下文拖得越长，即使模型标称支持，重要线索也越难被稳定用上，等待和费用还会增加。对支持相应长度的模型，**10 万到 30 万 token 的窗口对长聊已经很宽裕**；窗口大小不是每轮都要填满的目标。先清掉无关工具输出与旧话，再看是否需要更长的窗口。

## 记住重要的，不是记满所有的

用户说“最近有点累”，不等于确认了原因，更不等于以后每晚都应该被问一次有没有好转。

要判断一件旧事离现在多久，先得让宿主把**真实的当前日期、时间和时区**交给模型。旧摘要和消息顺序不能充当时钟；没有时间注入，就不能仅凭旧消息说“你又熬夜了”或“已经过了三天”。有了时钟，也要看那条近况何时说、用户后来有没有改口，不能把“上次在旅行”直接当成此刻仍在旅行。

角色可以根据关系表达想念、无聊、期待，这些不必每次都找一个外部事实来许可；但“你答应过”“你又熬夜”“你刚才在外面”需要实际依据。

这一点对第一人称与写作视角都成立：**看到了后台材料，不等于可以把所有材料当成角色亲眼见到的现实。**

## 长聊优先整理上下文

相比到达阈值后按轮数直接扔掉旧对话，本书更倾向于先试 **模型压缩摘要 + 保留近期原文**：让旧话题、已纠正的事实和仍有效的关系脉络留下来，同时把大段工具输出与过期过程清掉。摘要不是自动清洗器，写坏了照样会编事实、丢语气；要留原始对话的可恢复副本，观察压缩前后实际变化。

它解决的不是“让模型拥有一份漂亮的长期记忆”，而是上下文变长以后，尽量留下对下一轮仍有用的东西。直接按轮数删除很简单，却可能刚好删掉一条仍在进行的约定；完整保留又会把工具噪声、旧猜测和已经结束的过程一起带进来。摘要加近期原文，是在这两种损失之间做一个可检查的折中。

AstrBot 的[上下文压缩文档](https://docs.astrbot.app/use/context-compress.html)说明，默认策略是按轮数截断；选择 LLM 压缩时可指定摘要模型、保留近期轮次并调整摘要提示词。先在 WebUI 的“配置文件 → AI 配置 → 高级 → 上下文管理策略”里检查当前选项，再到“模型提供商 → 对话”核对模型的 `max_context_tokens`。如果窗口无法识别且仍为 0，自动压缩可能不会触发；没有选摘要模型时也可能退回截断。若另有“最多携带对话轮数”，也要确认旧对话是否早在摘要触发前就被裁掉。按你的版本界面和日志确认，别以为点了“压缩”就已经生效。

AstrBot 文档中的默认摘要模板会提到项目进度和工具调用。这对办事有用，对闲聊则未必是最想保留的内容。可以让摘要优先留下仍相关的话题、明确偏好、已确认的改变与尚未完成的约定，把旧工具日志压成必要结果；不要把推测、玩笑和未执行的动作写成既定事实。是否改模板，仍要看一份真实摘要，而不是仅凭名称判断。

可以先检查一份真实摘要：

- 用户的猜测有没有被写成确认事实。
- 开玩笑的话有没有被当作长期约定。
- 最近已经澄清的事情是否仍旧记错。
- 未完成工具是否被写成已完成。
- 是否保留了当前仍相关的互动，而只剩零散资料。

先修最明显的一项，再比较压缩后的聊天。不要同时换摘要模型、主模型、人设和记忆插件。

压缩本身还会调用模型，产生额外费用与一次出错机会。AstrBot 当前文档也说明，工具调用过程内部暂不压缩，压缩后仍超限时会继续裁剪；所以少挂高噪声工具和设置压缩策略是两件互补的事。

## 检索式记忆，默认可以先不用

本书不建议为了日常私聊一开始就安装自动记忆插件。常见实现会将选定的对话或提取结果入库、生成向量，查询时检索回相关片段；有的还会使用重排序，但不是每个插件都这样，也不是每条坏回复都会自动入库。关键要看它**实际收录什么、什么时候回注、能不能更正和删除**。

如果插件自动收录了误解、过期状态或一次不满意的角色回复，后续检索可能反复把它带回来。**即使清空原线程，只要相关记忆插件仍在回注旧材料，新会话也可能继续受影响。**长期使用还得同时维护原始会话、摘要和额外索引或数据库，并处理备份、删除及隐私范围。先用“近期原文 + 必要时的压缩摘要”聊一段；只有确实需要跨会话找回大量资料、愿意维护入库规则和纠错流程时，再单独试检索式记忆。

若要试，先限定一个会话、一个插件，抽查入库内容和回注片段，并实际试一次纠正与删除。不要把“检索命中”当成那段资料必然真实，也不要再同时启用另一份会注入相似资料的记忆插件。

## 只想删掉最近一次不满意的回复

不必为了一轮答歪的聊天就重写人设，或者直接丢掉整条会话。[llm_amnesia](https://github.com/SinkAbyss/astrbot_plugin_llm_amnesia) 提供 `/forget` 删除当前会话的最新一轮，`/forget 3` 删除最近三轮。想反悔可在接着聊天前用 `/cancel_forget` 恢复；要重新回答，自己再发一次消息。动手前备份重要对话，确认删的是当前会话。

例如，这一轮回答把普通闲聊误接成连环追问：

```text
用户：有点睡不着。
Bot：是不是还在想白天的事？要不要说说？现在觉得焦虑吗？
用户：/forget
Bot（插件）：✅ 已遗忘最新一轮对话
用户：刚才只是刷手机刷晚了，陪我聊两句。
Bot：好呀，我在呢。
```

如果只是这次回复把后文带偏，删去后可以按自己的意思重发；若每次都这样，就回到[第 9 章](09-debugging.md)检查人设、模型和注入，删历史不会修好生成方式。

`/forget` 改的是 AstrBot 会话里的历史，不会同时撤回 QQ 已显示的消息、删除旧摘要或清空其他插件的记忆库。如果旧内容又被检索注入，还需到对应的记忆插件里更正或删除。

## 换人设时，给旧对话一个干净的入口

情境：你改掉了角色卡里惯性追问的写法，却想保留过去聊过的事。比如旧会话里确实提过一本书最后几页很难校对，但 Bot 的回复总带一串追问：

```text
旧会话
用户：最后几页校对起来最费劲。
Bot：辛苦了，你一定很累吧？要不要休息一下？接下来打算做什么？
用户：不用一下问我这么多，我就想随便聊聊。

新会话（启用新人设，带入清洗后的摘要）
用户：总算校完了。
Bot：终于，最难改的那几页也弄完了。
```

新会话只沿用了用户说过的事和明确的表达偏好，没有把旧 Bot 的连问当成说话范本。完整迁移可以照下面的顺序做。

### 1. 把三份材料一起交给摘要模型

先备份并导出**旧线程的完整对话历史**，保留用户的改口、纠正和旧 Bot 不合适的回复，让摘要模型有材料判断什么该留下、什么只是旧示范。准备好将要启用的**新版角色提示词**。旧会话和新人设是两份不同的输入，不要先把新人设贴进旧会话继续聊。

打开[可直接发送给外部模型的摘要请求](../examples/conversation-handoff-prompt.txt)，把其中两处 `<<...>>` 分别换成自己的**新版角色提示词全文**与**旧会话完整历史**；后面的清洗要求一并保留。整段发给另一个大模型服务，网页聊天端也可以。旧会话太长时，可以作为文件上传，但要确认服务读到了全文。对外发送前在副本里删去不能分享的账号、密钥和私人内容；自己的角色卡可以提供，平台的隐藏指令不要附带。

请求会让它按长期主线、核心结论、最新焦点、技术细节、用户偏好、失败尝试和待办整理。重点是**保留发生过的事和明确偏好，清走旧回复的口癖与错误推测**，不是请外部模型扮演新角色，也不是让它重写新人设。

### 2. 核对摘要，准备放入历史

外部模型按模板返回一条带双引号的 **JSON 字符串**，内部分段用 `\n`，不是 `/n`。例如开头会像 `"【初始目标 / 长期主线】...\n【已讨论的核心话题与结论】..."`。核对用户改口有没有保留，旧 Bot 的猜测是否被写成事实，旧语气有没有混进“用户偏好”，未执行的约定有没有被写成已经完成。发现不对就先改摘要，不要带着错误进入新线程。

准备写入历史的正文是在摘要前加一行 `【历史对话摘要】`。例如摘要里确认了“最后几页校对最难”，就保留这件事；那串“要不要休息、下一步打算做什么”的旧问句不用搬进去。若历史以 JSON 保存，`text` 字段里的换行仍写成 `\n`；不要把外部模型返回的**整串带引号结果**再当作普通文字塞进 `text`，否则会多一层引号和反斜杠。

### 3. 用新人设建立新线程，再放入摘要

先在宿主启用**新版人设**，新建会话，发一句“你好”并等它回复，让新线程实际建立。找到**这个新线程**的历史并另存一份备份，不要改旧线程。在宿主允许编辑或更新会话历史的地方，把核对后的摘要作为一条 `user` 消息放到新线程历史开头，下一条 `assistant` 消息写“已收到”；下面保留新线程原有的“你好”和 Bot 回复。这样，新角色看到的是一份用户侧交接资料和自己的新会话，而不是一长串旧角色台词。[完整消息数组示例](../examples/conversation-handoff-history.example.json)用虚构的林夏展示这四条的顺序；摘要和“你好”后的回复，都要换成你自己新线程里的实际内容。

如果宿主要求在这条摘要消息的 `user.content` 里再放一个 `text` 项作为 `<system_reminder>Current datetime: ...</system_reminder>`，它应位于摘要 `text` 之后，并使用**新线程当时由宿主提供的实际时间**；若宿主会自行注入当前时间，就让它处理，不必手填。不要把旧线程的日期复制成新线程的“现在”。示例只放摘要项，没有写死日期。

上面的数组展示的是**历史消息内容**，不是可以直接上传的 AstrBot 数据库文件。管理页若只提供只读预览，就使用该版本确实支持的历史编辑方式；不要把导出的 JSON 当作可写入口，更不要直接改正在运行的数据库。如果宿主没有可靠的历史编辑方式，就在新会话里由用户正常发送一次 `【历史对话摘要】` 加核对后的正文，不需要手造一条“已收到”。

最后继续聊一两轮：看角色是否接住了真实近况，旧口癖有没有被带回来；如果其他记忆插件还会回注旧材料，也要单独处理。这里只是把旧信息交接给新人设，不会自动修好新人设或清空外部记忆库。

## 让角色活在当前时间里

如果每次请求都只有“用户刚刚说了什么”，角色其实被困在一个没有钟表的现在。宿主把当前时间交给模型后，夜里的“还没睡吗”、早上的“醒了吗”和下午的“今天过得怎么样”，才有了不同的落点；“十分钟后”“晚点再叫我”“明早提醒我”也不再只是含糊的台词，而可以进入实际安排。

例如：

> 用户：我先睡了，明早八点叫我。
>
> 普通回复：好，晚安。
>
> 更完整的私聊体验：角色先自然道晚安，同时把“明早八点再联系”交给宿主的调度能力。

这里的关键不是每轮都把日期时间复述一遍，而是让时间在需要它的时候发挥作用。宿主没有提供当前时间时，不要让角色凭空编造精确时间；宿主支持相对延迟时，也不必为了得到年月日而把简单的“十分钟后”问复杂。

## 让角色有机会先开口

朋友会因为想到你来找你，也会分享一件小事。主动消息的意义，是让 QQ 私聊不再只能由用户按下发送键开始：角色可以在沉默一段时间后发来一句“刚刚突然想到你”，或者接着昨天没说完的话继续聊。亲密角色也可以直接说想被陪着，不必把每次主动联系伪装成吃饭、睡觉或工作检查。

主动消息与 FutureTask 的区别，可以先用一句话记住：

- **主动消息**是“我现在突然想找你”。
- **FutureTask**是“我们之前约好，我到那个时间再来找你”。

两者都让角色拥有了主动性，但给人的感觉不同。前者像关系中的自然想起，后者像一次被记住的约定。频率、静默时段和暂停设置，是为了让这种主动联系落在用户愿意接受的范围内，而不是把角色的主动性删掉。

一种较清楚的偏好说明是：

> 我接受这个角色主动来找我，也接受普通的生活提醒。北京时间 23:00 到次日 08:00 不要主动发消息，暂时不回复时不要连续催。暂停以后不再主动联系，等我重新开启。

这是供使用者设定自己的范围，不是本书统一规定的时段或频率。角色的主动程度也可以不同。

### 插件触发的主动聊天

私聊里角色偶尔自己来找你，一般由宿主或插件在沉默一段时间后提供一次生成机会。例如 [astrbot_plugin_proactive_chat](https://github.com/DBJD-CR/astrbot_plugin_proactive_chat) 可以按会话间隔触发主动消息，并让你设置会话、免打扰时段、未回复次数上限和主动消息提示词。这样配置后，模型才有机会把“想你”“想分享”“想被陪”写成一条真正发出去的消息，而不是只在用户下一次发言时顺便提到。

![私聊中主动发出的两条消息](../assets/book/06-proactive-chat.png)

主动消息也要接住已有对话；像“忙了一上午”这样的近况，应来自确知的上下文，而不是由触发时间猜测。

这类插件可能用模拟的用户消息启动一次模型请求。为了让模型写出“角色自己来找你”的消息，`proactive_prompt` 需要把这次机会和普通用户发言区分开，同时沿用当前会话的人物。下面是一个简例；两个双花括号字段是此插件提供的占位符，换插件要按它的实际字段改：

```text
【主动联系】
这是宿主触发的一次私聊主动发言机会，不是用户刚发来的话。沿用当前会话的人设与关系，写角色这次自己想说的话。
当前时间：{{current_time}}
连续未回复次数：{{unanswered_count}}
角色可以因为想念、无聊、想分享或想被陪而开口，不必先问用户在忙什么。旧话题可以顺带提，但不把过去的状态当成现在的事实；未回复次数不证明用户故意不理你。只输出发给用户的消息，不附任务说明。
```

这段只告诉模型“为什么此刻有机会开口”，不替不同角色规定语气、长度或气泡数。角色本来会撒娇，就让人设决定她怎么撒娇；插件负责提供机会和发送路径。

先只给一个获准的私聊会话启用，核对主动消息的实际显示、停发和收到用户新消息后的行为。若另一插件也会主动发信，检查它们是否会在相近时间重复联系同一个人。

## FutureTask：让“之后再联系”真的成为聊天的一部分

普通聊天模型只能在收到消息时回答。你说“明早叫我”，它最多只能当场回一句“好”；如果没有宿主的时间和调度能力，明早并不会因为这句台词自动到来。FutureTask 补上的，正是这段从**现在的约定**到**未来的消息**之间的联系。

它适合这样的私聊：

> 用户：我去睡了，明早八点记得叫我。
>
> 角色：好呀，晚安。明早八点我来叫你。
>
> 到时间：角色再次在 QQ 发来消息。

这样一来，角色不只是对当前消息作答，还能参与“等会儿”“明天”“下次”的生活安排。提醒本身不必很正式，可以是角色自然的一句话；重要的是，用户确实能在未来收到这次联系，而不是只在当下听到一句好听的承诺。

FutureTask 与主动消息插件的分工也因此清楚了：主动消息是角色临时想起你，FutureTask 是你们已经约好的未来联系。一个制造偶遇，一个兑现约定；两者同时存在时，QQ 上的角色才既有自然的主动性，也有对时间承诺的记忆。

一条未来联系大致经过这几个步骤：

```text
角色表达打算
  → 模型发起有效调用
  → 宿主接受并创建任务
  → 到时触发
  → 任务执行
  → 消息投递
```

![FutureTask 的已注册任务列表](../assets/book/04-future-task-redacted.png)

任务列表的意义，是让这次约定不只存在于聊天文字里：你能看到它的名称和计划时间，也能在需要时修改或删除。具体入口和工具名称随 AstrBot 版本变化，配置时按当前宿主提供的任务能力填写。

### 保留主动性，不把授权写成层层关卡

用户可以直接请求提醒，也可以事先授权一类日常提醒或稍后联系。已经有适用的持续授权时，不需要每次重新征求同样的许可。

时间不精确时，也不必总是反问。若授权范围允许、场景足以作出低风险的合理选择，可以按可用工具安排并让用户知道；真正无法判断或后果明显不同，再澄清。

相反，面向新收件人、修改重要资料、付费等动作，不应从“允许主动私聊”里顺手推出授权。这是在区分动作范围，不是在把普通联系变成审批流程。

### 失败也要保留事实

配置时最值得确认的不是模型有没有说“记住了”，而是任务列表里有没有出现这次约定。成功后，角色可以自然地说“好，明早见”；如果创建失败，就直接告诉用户这次没有安排上，而不是用角色口吻把失败盖过去。

## 做一次小验收就有帮助

从一个几分钟后触发、容易删除的测试任务开始：

1. 创建后看任务列表，确认约定真的留下来了。
2. 到点看角色是否在正确的 QQ 会话里再次开口。
3. 删除一个测试任务，确认这次约定可以被收回。
4. 如果你依赖重启后仍有效，再单独检查任务是否保留。

主动聊天与普通回复还要共享同一套人物设定。插件触发入口和任务入口都不应突然变成另一种口吻，也不应绕开你已经设置的暂停。

对于日常陪伴，FutureTask 让角色拥有了“之后还会回来”的时间感。重要提醒则应另外使用你信得过的提醒渠道。
